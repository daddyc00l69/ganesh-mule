MASTER PROMPT: Production-Ready Full-Stack E-Commerce Platform

Act as a senior full-stack software architect, UI/UX designer, database engineer, security engineer, and DevOps engineer.

Build a complete, production-oriented e-commerce web application where customers can purchase products online, administrators can manage the business, and managers can handle orders, inventory, and customer support.

Do not create only a UI prototype. Build a working full-stack application with a real database, authentication, authorization, backend APIs, payment integration, inventory management, and customer support integration.

Work incrementally, test the implementation, and document all setup instructions.

1. PROJECT OBJECTIVE

Build an e-commerce platform with three main interfaces:

Customer-facing online store.
Admin dashboard.
Manager dashboard.

Use the Solid Glass design reference for the Admin and Manager dashboards:

https://deeplethe.github.io/solid-glass/

Study the reference website first. Reproduce its visual language, layout, component styling, colors, typography, glass effects, navigation, spacing, and responsive behavior as closely as practical.

Do not assume that the reference website provides a compatible component library or npm package. Inspect its available implementation and use compatible components or recreate the design system with the chosen frontend technologies. Do not copy unavailable source files or invent library APIs.

The customer-facing store should have its own polished e-commerce design while remaining visually consistent with the overall brand.

Server-side session validation.
Session expiration and logout.
Password reset using expiring, single-use tokens.
Rate limiting for login, password recovery, and sensitive actions.
Input validation with Zod.
CSRF protection where required by the chosen authentication architecture.
Protection against brute force, session fixation, privilege escalation, and IDOR.
Audit logging for sensitive administrative actions.

Protect admin and manager routes with server-side authorization. Redirect unauthorized users appropriately.

Do not store authentication tokens or sensitive secrets in localStorage.

Never log passwords, session tokens, payment secrets, or full payment credentials.

9. RAZORPAY PAYMENT INTEGRATION

Integrate Razorpay using the current official documentation:

https://razorpay.com/docs/

Requirements:

Use Razorpay test mode during development.
Keep the Razorpay key secret on the server.
Create payment orders through a protected backend endpoint.
Calculate the payable amount on the server.
Store monetary values as integer minor units, such as paise for INR.
Create a local order and payment record with appropriate pending states.
Associate the Razorpay order ID with the internal order.
Open Razorpay Checkout on the frontend.
Verify the checkout payment signature on the backend using the official documented algorithm.
Never treat an unverified browser callback as proof of payment.
Verify webhook signatures using the raw request body and webhook secret.
Handle duplicate and out-of-order webhook events safely.
Store webhook event IDs and make processing idempotent.
Reconcile payment status with Razorpay when necessary.
Handle success, failure, timeout, retry, and abandoned checkout.
Prevent duplicate charges and duplicate order fulfillment.
Record payment attempts and state transitions.
Support refunds through authorized server-side workflows.
Update the order's payment status only after verified evidence.
Keep payment state separate from fulfillment state.

Use explicit statuses such as:

CREATED
PENDING
AUTHORIZED, if applicable to the configured flow
PAID
FAILED
REFUND_PENDING
PARTIALLY_REFUNDED
REFUNDED

Use valid transitions based on the actual Razorpay payment lifecycle.

Never store card numbers, CVVs, UPI PINs, or other sensitive payment credentials.

Provide webhook configuration instructions, test cases, and reconciliation procedures.
